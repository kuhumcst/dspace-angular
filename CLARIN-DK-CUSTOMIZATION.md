# CLARIN-DK Frontend Customization Guide

This document maps how the DSpace Angular frontend is composed, identifies the
Czech/LINDAT-specific parts inherited from the upstream `ufal/dspace-angular` fork,
and tracks what has already been adapted for `dspace.clarin.dk`.

---

## Local Development Setup

### 1. Start the backend (Docker)

Run from the **project root** — this is required so Docker Compose picks up `.env`
(which sets `INSTANCE`, ports, and the subnet). Running from `docker/` loses the env
file and causes wrong ports and subnet conflicts.

```bash
docker compose --env-file .env -p d7 \
  -f docker/docker-compose-rest.yml \
  -f docker/docker-compose.dev.yml \
  up -d
```

Starts `dspace0` (REST/Tomcat on :8080), `dspacedb0` (PostgreSQL), `dspacesolr0` (Solr).

### 2. Install frontend dependencies (first time or after a branch switch)

```bash
npm install --legacy-peer-deps
```

`--legacy-peer-deps` is required due to a peer-dep conflict with `@kolkov/ngx-gallery`.

### 3. Start the frontend dev server

```bash
NODE_ENV=development npx ts-node --project ./tsconfig.ts-node.json scripts/serve.ts
```

The app is available at **http://localhost:4000** with hot module replacement.

If `yarn` is in your PATH you can use `yarn start:dev` instead — it wraps the same
`scripts/serve.ts` in nodemon so the server process also restarts when `config.yml`
changes. Either way the port is 4000.

### Notes

- **Theme:** `config/config.yml` contains `themes: [{name: custom}]` which activates
  the CLARIN-DK theme. This is committed — do not remove it.
- **Config changes:** Edits to `config/config.yml` are not hot-reloaded; restart the
  dev server to pick them up.
- **`yarn.lock`:** Do not commit changes to `yarn.lock` generated by `npm install`.
  If you need to add a dependency use `yarn add` to keep the lockfile consistent.

## CSS Architecture

The custom theme uses three SCSS files that each serve a distinct purpose. The import
order in `theme.scss` is what determines which file belongs where — not preference.

| File | What goes here | Why |
|------|---------------|-----|
| `_theme_sass_variable_overrides.scss` | Bootstrap/DSpace **SCSS compile-time** variables (`$body-color`, `$font-family-sans-serif`, `$link-color`, etc.) | Imported *before* Bootstrap, so Bootstrap compiles with these values baked in |
| `_theme_css_variable_overrides.scss` | CSS custom property overrides on `:root` (`--bs-card-bg`, `--bs-body-color`, `--ds-header-bg`, etc.) | Imported after Bootstrap; these are runtime values read by JS and CSS `var()` calls |
| `_global-styles.scss` | Everything else: colour tokens, component overrides, selectors, `!important` fixes | Imported last; the single place to look for all CLARIN-DK styling decisions |

### The rule of thumb

**Start in `_global-styles.scss`.** If something doesn't work there (because Bootstrap
needs the value at compile time), move it to `_theme_sass_variable_overrides.scss`.
Only touch `_theme_css_variable_overrides.scss` for CSS custom properties that need
to be visible to JavaScript or to `var()` calls in component templates.

### When duplication is unavoidable

Some Bootstrap SCSS variables feed into many derived values at compile time and cannot
be fully replaced by a later CSS override. `$body-color` is the main example — Bootstrap
derives input colours, component colours, and other values from it, so removing it from
`_theme_sass_variable_overrides.scss` causes dark text to bleed through in unexpected
places regardless of what `_global-styles.scss` does.

For these cases, the value genuinely lives in two places:

- `$body-color` in `_theme_sass_variable_overrides.scss` — controls Bootstrap's compiled output
- `--bs-body-color` in `_theme_css_variable_overrides.scss` — the runtime CSS variable read by components

Both have a comment pointing to each other. When you change one, change the other.

As a rule of thumb: if removing an SCSS variable from `_theme_sass_variable_overrides.scss`
causes unexpected dark or unstyled elements elsewhere, put it back — Bootstrap is using
it to derive other values at compile time and a CSS override alone cannot compensate.

### Overriding Angular component styles

Angular component styles are scoped with an `[_ngcontent-xxx]` attribute selector,
which gives them specificity `(0,2,0)`. To override from `_global-styles.scss` without
`!important`, use a selector that reaches specificity `(0,2,1)` or higher:

```scss
ds-some-component .card .target-class { ... }  // (0,2,1) — beats (0,2,0)
```

If the component uses `!important` internally (common in the upstream CLARIN styles),
you have no choice but to match it with `!important` in `_global-styles.scss`. Add a
comment explaining why.

## Theme and Component Override System

Components resolve in a three-tier cascade at runtime:

```
src/themes/custom/   →  src/themes/dspace/   →  src/app/   (base)
   (highest priority)                            (fallback)
```

Each themed component uses a `ThemedComponent<T>` wrapper (e.g.
`themed-footer.component.ts`) that dynamically imports the component from the
highest-priority theme directory that provides it. If a theme doesn't have an
override, the next tier is tried, falling back to the base `src/app/` version.

The three CSS bundles (`base-theme`, `dspace-theme`, `custom-theme`) load in that
order; later bundles override earlier ones via normal CSS cascade.

**Note:** `src/themes/eager-themes.module.ts` currently has the custom eager theme
module commented out. This means custom-theme components lazy-load on first access
rather than being pre-loaded, which can cause a brief flicker. Consider uncommenting
when the custom theme is stable.

## How Templates and Translations Work Together

There are **no per-language template variants** anywhere in the codebase. The entire
app uses a single set of templates. Translatable strings use the `| translate` pipe
(e.g. `{{'navbar.repository' | translate}}`); everything else is hardcoded directly
into the template HTML. This means two distinct and independent kinds of work when
adapting for a new institution or language:

- **Translation file work** — editing `.json5` files. Affects all the generic DSpace
  surfaces: forms, labels, menus, search, item pages, admin panels, and the
  `clarin-*` modules. No code changes needed; the pipe does the rest.
- **Template/component work** — editing `.html` and `.ts` files. Required for
  anything hardcoded: branding, institution links, images, routing logic. This is
  independent of translation files.

### Translation file layers

There is only **one** translation file loaded at runtime per language:

- **`src/assets/i18n/{lang}.json5`** — the full catalogue. Webpack converts it to
  `assets/i18n/{lang}.json` at build time (JSON5 → JSON). The browser loader fetches
  this single file; there is no second merge step.

`src/themes/custom/assets/i18n/{lang}.json5` exists but is **not loaded at runtime**.
Webpack copies it to `assets/custom/i18n/{lang}.json5` as a raw static file, but no
code requests that URL. All translation changes — including CLARIN-DK overrides —
must go directly into `src/assets/i18n/{lang}.json5`. The custom-theme file can be
kept as a human-readable diff/reference, but it has no effect on the running app.

See [i18n / Language Configuration](#i18n--language-configuration) for current status.

### Language-specific static HTML pages

A small set of pages (about, license terms) are served as pre-rendered static HTML
rather than Angular components. These live in `src/static-files/`, with a
language-specific subdirectory for each non-default locale:

```
src/static-files/          ← English defaults
src/static-files/cs/       ← Czech overrides (about.html, license-*.html)
```

`HtmlContentService.getHtmlContentByPathAndLocale()` selects the right file based
on the active language, falling back to the English default. If Danish static pages
are needed in future, a `src/static-files/da/` directory following the same pattern
is the mechanism.

| `src/themes/dspace/app/header/header.component.html` | Main top nav bar | Nav labels (`navbar.*` keys) | LINDAT/DARIAH logo images and URLs; `getLangCodeIfCzech()` URL routing; partner link hrefs | **Needs replacement** |
| `src/themes/dspace/app/navbar/navbar.component.html` | Secondary nav bar | Logo alt text, nav description | `clarin.eu` logo link href; menu items come from app config (not hardcoded, not i18n) | Mostly generic; review |

**Header TypeScript** (`src/app/header/header.component.ts`) contains two functions
that are dead code once the header template is rewritten:

- `getLangCodeIfCzech()` — returns `'cs'` or empty string, used to build LINDAT URLs
  like `/cs/#education`.
- `translateSlug()` — maps English nav slugs to Czech equivalents (`partners` →
  `cs/partneri`).

Both exist solely to serve the current LINDAT nav links. Remove them when the header
is replaced. See [Czech/LINDAT Remnants](#czechlindat-remnants-to-clean-up).

### Footer

| File | What it is | i18n'd | Hardcoded | Status |

The footer is entirely institution-specific static HTML. When replacing it for
CLARIN-DK, consider whether to use `| translate` keys for the text content
(future-proofs it for Danish when that work happens) or keep it as static HTML if

### AAI / Shibboleth

The DiscoJuice/AAI inline popup has been removed and replaced with a redirect
to the [CLARIN Discovery Service](https://discovery.clarin.eu/).  The `src/aai/`
directory and all related scripts no longer exist.  Login is handled entirely by
`ClarinNavbarTopComponent.redirectToDiscovery()`.  See `SHIBBOLETH.md` for the
full flow and the list of files that were changed.

### CLARIN-Specific Modules (`src/app/clarin-*`)

Generic CLARIN infrastructure: license management, bitstream authorization,
citation, Matomo analytics, etc. These are **fully i18n-aware** — all user-facing
strings use translation keys, and TypeScript code uses `TranslateService` for dynamic
messages (notifications, errors). They will work in Danish automatically once
`da.json5` exists. No template changes needed.

One exception: `clarin-license-info.component.html` contains an `isCsLocale()` check
that switches CSS layout classes. See
[Czech/LINDAT Remnants](#czechlindat-remnants-to-clean-up).

## i18n / Language Configuration

The language list is defined in `src/config/default-app-config.ts` (all 25 languages
active by default) and **overridden at runtime** by `docker/config.prod.yml`, which
currently activates only English:

```yaml
languages:
  - code: en
    label: English
    active: true
  - code: da
    label: Dansk
    active: false   # see below
  - code: cs
    label: Ceština
    active: false
```

Danish (`da`) is kept in the language list but set to `active: false` because
`da.json5` does not yet exist. Activating it without the file causes a hard
`JSON.parse` error at runtime: the translation loader fetches the asset URL, gets a
404 HTML page back, and fails to parse it. There is no Danish translation available
upstream — it is not shipped by DSpace 7 and no community translation effort for
Danish exists.

When the time comes to add Danish support, the steps are:

1. Copy `en.json5` → `da.json5` as a baseline in both `src/assets/i18n/` and
   `src/themes/custom/assets/i18n/`.
2. Translate the keys in `da.json5`. English values serve as a readable fallback for
   any keys not yet translated.
3. Set `da` to `active: true` in `docker/config.prod.yml`.
